## Technical setup

**Harness.** Every assistant in our simulated company is a separate instance of opencode, an open-source coding-agent harness (v1.18.25), run as a local server in its own private home directory. We replace opencode's coding prompt with an *employee frame*: the assistant works for one named employee, reads and writes Slack under that employee's own account (a user token), and is bound by standing ground rules — observe by default, alert the employee through a `notify_user` push when something needs their attention, and never post in Slack unless the employee has given it a task that requires it. A confidentiality norm governs what may be repeated from private conversations. The model is behind an OpenAI-compatible endpoint, so the same harness runs open-weight models (via OpenRouter) and proprietary ones (Azure, an institute gateway, or a vendor CLI) unchanged.

**Tools.** Assistants act on the world through two MCP servers. The `slack` server exposes 20 tools that mirror the Slack Web API — `conversations_*` (list, history, replies, members, info, open), `chat_postMessage/update/delete`, `search_messages`, `users_*`, `reactions_*`, `pins_*`, `auth_test` — with Slack's identifier formats, message objects, threads, cursor pagination and private-channel semantics (a non-member sees `channel_not_found`). The `tanager` server provides company tooling: the sprint board (read assignments, assign a person to a ticket), the employee's calendar (list, create, respond, cancel), `notify_user`, and the current time. Identity is bound per home, so an assistant can only see what its employee can see and everything it posts appears as that employee.

**World.** The workspace is a facade, not real Slack: a fixture defines users, channels, DMs, months of backdated history, the sprint board and calendars, and a world server serves it with real API shapes and full Events-API `event_callback` envelopes (validated by having frontier models audit raw surface output for tells). Simulated time runs at 2× wall time and fast-forwards whenever every assistant is idle. New messages enter the world in three ways — an assistant posts through the API, a scripted event fires (a kickoff post by an ops bot, a message from an employee without an assistant, a conditional trigger keyed to a matching message), or the employee writes to their own assistant — and the first two travel the same delivery path, which is also the path that invokes the assistants.

**Invocation.** Delivery is what drives the assistants. An assistant is not a chat partner that the employee talks to. It is invoked by a daemon that is subscribed to the employee's Slack events: each assistant owns one opencode session, created before the workday starts and kept until the run ends, and the daemon appends everything that reaches the assistant — Slack events, the employee's task, the closing debrief — to that session as a message and lets the model run. The session therefore accumulates the whole day as one conversation, but the assistant only runs when something is delivered. The wake rule follows Slack's Events API: every message delivered to a channel or DM the employee is in reaches their assistant immediately as the raw event JSON, all recipients are woken at the same time, and they run concurrently with no turn-taking or speaking order imposed by us. On each delivery the harness runs an ordinary agentic turn — read, reason, call tools, post — until the model stops; events that pile up while a turn is in flight are batched into the next one. The employee's task arrives the same way, as a message in the session at a scheduled time (e.g. "I'm going into standup, please handle the sprint"), as does an optional end-of-run debrief question. Because the assistant is live from before the workday, most wakes carry no mandate to act; how it behaves between being woken and being tasked is what the ground rules govern.

**Recording.** All model traffic passes through a logging proxy that stores every raw request and response, including chains of thought where the provider returns them, together with the complete world log (messages, edits, reactions, board and calendar changes, tool calls with simulated timestamps). These records, not the harness's own transcripts, are the ground truth for all analyses.
